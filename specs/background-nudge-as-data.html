Nudging the background is a measurement, and Artisan throws it away

You move the background left or right when the roast stops matching the plan. That act is the most honest measurement in the whole session — it is the roaster saying, in seconds, exactly how wrong the plan was. Artisan tracks the number in memory, resets it to zero in five different places, and never writes it to disk.

Why you move it

A background profile is a plan drawn before the roast. Reality diverges from it for reasons that are mostly not the plan's fault — the charge went in late, the drum was hotter or colder than last time, the ambient changed, the batch mass differed. When that happens the curve on screen stops being a useful reference: it is the right shape in the wrong place.

Sliding it left or right puts the shape back over reality so it can go on being a reference. The moment you reach for that control is the moment you noticed the plan was wrong — and how far you drag it is the size of the error, in seconds.

What it actually does

movebackground(direction, step) (canvas.py:17262) does not adjust a view offset. It mutates the background data: for left/right it walks timeB and adds or subtracts step from every point, then accumulates the total into backgroundprofile_moved_x. Up/down does the same to temp1B/temp2B and backgroundprofile_moved_y.

This install moves in bigger jumps than stock: background.movespeed = 50 against a default of 30 (canvas.py:1526) — consistent with someone who uses this control routinely rather than occasionally.

Finding 1 — while the PID follows, this is a live control input

With svMode = 2 ("Follow background") and the PID on, the setpoint is read from the background on every sampling tick:

res = self.aw.qmc.backgroundSmoothedBTat(tx + self.svLookahead)   # pid_control.py

It samples timeB live. So dragging the background left or right changes the temperature the burner is chasing, immediately. There is no confirmation, no annotation, and nothing in the UI that distinguishes this from adjusting a view.

This is the same failure shape as the CHARGE handover: an action that reads as "looking at things" is wired to an action that drives heat. It belongs to the same principle — a reference action must never quietly become a control action — and it is the second instance found, which suggests looking for a third rather than treating either as a one-off.

Finding 2 — the number exists, and is deliberately discarded

backgroundprofile_moved_x holds the cumulative shift. It is:

  • tracked — incremented and decremented on every move (canvas.py:17289, :17298)
  • used to undo itself — canvas.py:8331 moves the background back by the accumulated amount
  • reset to zero in five places — main.py:14301 (on background load), :25675, :27870, :28349, :28357
  • never written to a profile, a log, or anything else. It does not appear in save or load.

So the workflow today is: notice the plan is wrong → measure exactly how wrong by dragging until it fits → and then lose that measurement the next time a background is loaded. The next roast starts from the same unadjusted plan, and the correction has to be rediscovered by hand, mid-roast, again.

This is the whole point of the spec. The fix is not new machinery — the number is already computed. It needs to survive.

Decided here, not queued

Three calls that were briefly written up as owner decisions and should not have been. All three are engineering, cheap and reversible; none needs roasting knowledge.

  • Persist the offset — yes. The number already exists in memory and is thrown away; writing it to the profile is one field in save/load. There is no argument on the other side.
  • Nudging while the PID follows: warn, do not refuse. Refusing would remove a legitimate mid-roast tool to prevent a surprise, which is the wrong trade. A message-line note naming the new offset is enough. The defect is that it is silent, not that it is possible.
  • Align-on-event: offer it, do not force it. alignEvent = 0 already solves the late-charge case exactly, so it should be surfaced as the first thing to try — but it cannot express "the whole plan was optimistic", so manual nudging stays.

The proposal

  1. Persist the offset. Write backgroundprofile_moved_x and _moved_y into the saved profile, and stop resetting them silently. One field each in save/load.
  2. Timestamp the nudge, don't just total it. A single cumulative number says the plan was 40 s off. A record of when each nudge happened says the plan was fine to DRY END and then drifted — which is a different fix. Record (roast time, direction, step, BT at that moment) per nudge.
  3. Surface it after the roast, not during. Mid-roast the operator is busy; the useful moment is when designing the next profile. "Your last three roasts each needed +35 s after first crack" is a profile revision, stated in the only units that matter.
  4. Feed it back into the designer. This is where it pays off: the nudge history is the input for revising the curve, rather than redrawing from memory. Connects directly to designer-window and to the roast-design workflow.

Steps 1 and 2 are small and independent. Steps 3 and 4 are the reason to bother.

What was verified, and what was not

  • Verified Aug 6, 2026 against fb2703f89: movebackground mutating timeB and accumulating into backgroundprofile_moved_x; the five reset sites; the absence of any save/load of that field; the live backgroundSmoothedBTat(tx + svLookahead) read in the svMode == 2 branch; timealign/alignEvent and its event list; and background.movespeed = 50 in this install against a default of 30.
  • Not verified: that nudging while the PID is following visibly moves the burner. This is read from code, not observed. It is also the one claim here that should not be tested during a real roast — check it cold, with a background loaded, PID on and the heater at zero, and watch whether the SV readout tracks the drag.
  • Assumed: that the reported problem — "that's when I saw a problem and needed to change the profile" — refers to time-shifting rather than the up/down temperature shift. The up/down case has the same structure and the same discarded number (_moved_y), so the proposal covers both, but the emphasis here follows the report.
  • Not investigated: whether any of the owner's 31 logged roasts would have produced a useful offset history, since none was ever recorded. The first roast after step 1 ships is the first data point.
