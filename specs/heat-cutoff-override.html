Who cuts the heat at 165 °C, and can software override it

Every roast on this machine dies in a 14 °F band. Artisan's four automatic DROP paths are ruled out by measurement, and one roast proves the machine cuts its own heat unprompted — but nobody has yet watched the wire at the moment it happens, and that single recording decides whether this is fixable in software or is a machine limit to design around.

The one thing that would settle it

Capture every serial frame through a roast that reaches the cut, and read what crosses the wire in the two seconds around AH going to 0.

  • If {[AH 0]} appears from Artisan → software-issued, find the caller, override it.
  • If AH:0 appears in a machine response with no preceding write → machine-issued, and the question becomes whether {[AH 1]} re-enables it.

No such capture exists. The bridge relays frames but does not record them — verified Aug 7, 2026: grep -n "_log" artisan_mcp/roaster.py logs port open/close only, and the audit log holds decisions (write, arm, probe), never wire traffic. Phase 1 is one file.

Every cut falls between 160.3 and 168.8 °C. This machine is configured in Fahrenheit but almost certainly computes in Celsius (see kaleido-machine-adaptations Finding 1), so a limit near 165 °C is a rounder number than the Fahrenheit spread suggests.

It is not new and not caused by Artisan's PID. The same AH transition appears in December 2025, January, April and June 2026 logs — 1000 g batches running the machine's own program, long before Artisan was driving the setpoint. Written down because the obvious hypothesis is that the recent PID work caused it, and the logs say otherwise.

It is soft, not a hard ceiling. b13 (2026-01-25_1411) reached 347.9 °F and b01/b02 reached 341.6. So the limit is exceedable under some condition nobody has identified — which is itself evidence that it is a setting rather than a fuse.

Artisan's automatic DROP paths are all ruled out

This matters because ArduinoPID.pidOffDROP = True: marking DROP cuts the burner within seconds, so any stray DROP mark looks exactly like a machine fault. Each path checked individually, Aug 7, 2026:

  • Auto-DROP (canvas.py:5180, fires above 320 °F, 7 min in, on a BTbreak() dip) — was the cause of the #23/#24/#26 cuts. Now disabled: defaults read org.artisan-scope.Artisan autoDrop → 0, and it survived Artisan's own quit-and-rewrite. #28 and #29 cut anyway.
  • Kaleido event flags — provably inert on this machine. Finding 2 established sid is always 0, so sid & 15 can never produce the DROP flag. The setting is also absent, so all seven default False.
  • Background playback DROP — backgroundPlaybackDROP defaults to False (canvas.py:1572) and is absent from the plist.
  • Alarms — the two installed are action 19 (PID ON) and 1 (Call Program). Neither can mark DROP; that is action 14.

The counter-example that carries the argument

In #_26-08-06_1717.alog, timeindex[6] = 0 — DROP was never marked — and AH went 1→0 at BT 331.2 °F while Artisan's PID was still commanding HP 80. Artisan cannot have cut the heat there. Something machine-side did.

The other five all show DROP landing ~3 s before the AH fall, which is the pidOffDROP signature. But that ordering is not trustworthy at this resolution: AH is a smoothed extra-device curve sampled at ~1 Hz, so a real machine-side cut could plausibly render three samples late, behind a DROP the operator pressed on seeing the heat die. Phase 1 exists because this ambiguity cannot be resolved from .alog files at all.

What we cannot observe, and why it constrains the method

Finding 3 is load-bearing here: this machine never reports HS, the "heater is firing" flag. So there is no confirmation signal for heat at all. HP is a commanded value and keeps reading 80 or 90 after the cut; AH is the only machine-reported heat state available.

Consequently every experiment below infers heat from BT actually rising, not from any status word. An {[AH 1]} that is acknowledged but changes nothing would be indistinguishable from success on the status word alone.

Phase 1 — record the wire (no writes, nobody needed)

Add frame logging to the bridge. Every request and response, with a monotonic timestamp and direction, appended as JSON lines to ~/.artisan-mcp/frames.jsonl.

  • artisan_mcp/roaster.py — log in SerialLink.request(), which already has both the outgoing frame and the response line in one place.
  • artisan_mcp/bridge.py — tag direction (artisan for relayed requests, bridge for injected ones, machine for responses) so a write from Artisan is distinguishable from one the bridge injected.
  • Rotate or cap the file: a 20-minute roast at ~1 Hz is only a few thousand lines, so size is not a real concern, but an unbounded log across many roasts is.

Then run one roast through the bridge to the cut. This requires reconfiguring Artisan to Kaleido-over-network (Config ▸ Device ▸ Kaleido, 127.0.0.1 : 8765) so the bridge owns the serial port — reversible in the same dialog.

Read the capture around the AH transition. That answers the top-level question without writing anything to the machine.

Phase 2 — if machine-issued, characterise the limit (still no writes)

All read-only, all safe to run repeatedly:

  • Does AH return on its own? The owner's restart-the-roast workaround suggests it does. The capture will show whether AH flips back to 1 spontaneously, or only after Artisan re-initialises the connection.
  • Is the trigger BT or ET? BT at the six cuts spans 160.3–168.8 °C; compute the ET spread across the same events. If ET is tighter, the machine is limiting on air/element temperature and the fix is airflow, not setpoint.
  • Is there a readable limit variable? The known tags are BT ET AT TS HP FC RC AH HS EV CS SC CL SN TU PI RD. Probe for an unlisted one with a bare read. This is guessing — flagged as such, and worth perhaps twenty minutes, not an afternoon. A bare read of an unknown tag returned {0} for TU and SN already, so a null result is uninformative rather than conclusive.

Phase 3 — can it be overridden (writes; owner at the roaster)

Ordering is not optional here. kaleido-machine-adaptations closes by stating that no write has ever been sent to this machine, and that the first should be a fan or drum command on a cold empty machine, watched. That guardrail governs this phase; do not start at step 3.

  1. Cold, empty, watched: {[FC 30]}. Establishes that this machine accepts a write at all, and what it acknowledges with. Nothing here is roast-critical.
  2. Cold, empty, watched: {[AH 1]}, then poll RD A0. Does AH read back 1, and does it stay 1? This is the override mechanism tested with no heat in the drum and no beans at risk.
  3. Mid-roast, owner at the machine, hand on the panel: when the capture shows AH fall, inject {[AH 1]} and watch BT. Heat resumed is the only proof; an acknowledged frame is not, because HS does not exist here.

Step 3 is the experiment that answers the title. It is also the only one that puts heat into a drum holding beans, and it must not be run unattended.

Decisions

Both are stated in the meta tags so specs.sh prune surfaces them; repeated here so the reasoning survives.

  • Authorise writes to the physical roaster for this investigation? Recommended yes, staged as ordered above. Phases 1 and 2 answer most of the question with no write at all, so the authorisation is only needed once the read-only evidence points at an override being possible. Blocks Phase 3 only.
  • If the cut is machine-issued and non-overridable, retarget to 335 °F? Recommended yes. 32 completed roasts cluster at a 328 °F median with the band running 323–338; the owner's tasting notes record 335 golden and 339 burnt. The reliable ceiling and the preferred result are the same number, so 350 was always fighting the machine for a worse roast. Does not block.
