Two roast designers, and only one of them Claude can use

Asked directly: am I using the roast designer tool? No — and neither does the established workflow. Curves for this machine are generated by a 205-line script that lives outside this repository, while the designer in the fork has never produced one. Two tools now make background profiles, they know different things, and neither knows what the other knows.

Taken and done, Aug 7, 2026 — make_roast_curve.py is in the repo

Answered rather than queued: where a file lives is an engineering call, and "the only tool that has ever produced a curve for this machine is outside version control" needs no roasting knowledge to resolve. Now at tools/make_roast_curve.py.

Copying it exposed that it was never self-contained. It reads a template profile — Designer/designer_2025-06-25_0000_nut-roast-338f-corrected-background.alog, 51 KB — which supplies every field the script does not compute: device config, event types, roast metadata. That is what makes the output a profile Artisan will load rather than a bare pair of arrays. Run from anywhere else it died with FileNotFoundError. The template is now carried alongside it, and resolution tries the script's own directory first, then the original working location, with --template to override.

The original is deliberately left in place. ~/.claude/commands/roast-design.md line 13 still invokes python3 make_roast_curve.py by bare name, so moving the file would have broken the /roast-design workflow silently. Both copies run and produce identical curves — verified from each location.

Verified: generates 1,037 points over 34.5 min, CHARGE 190.9 °F → DROP 349.9 °F, tail continuing to 368 °F past DROP, all five profile keys Artisan requires, timeindex with DROP at 825.

One claim checked rather than trusted: the script prints "strictly declining: True", and a naive per-sample rate of rise disagreed. It was right and the check was wrong — the apparent rises are all after t=2048 s, the post-DROP cool-down decelerating, and DROP is at ~1650 s. Recorded because the next person will compute RoR the naive way and think they have found a bug.

Remaining duplication is a real cost. Two copies of a 205-line script will drift. Converging them means editing roast-design.md to call tools/make_roast_curve.py by path and deleting the original — one line, but it changes a command outside this repository, so it is left for the owner.

The honest answer first

I have read the designer's code, screenshotted it once, and fixed its units. I have never used it to design a roast. When this project actually needs a curve, the /roast-design command does not open the designer at all — it runs:

python3 make_roast_curve.py --target 350 --out Designer/nut-roast-350F.alog

That is the real workflow, and it is not an accident. The script is usable by an agent because it is a function of its arguments; the designer is usable by a human because it is a window full of fields. Neither can do the other's job today.

Why the designer cannot be driven by an agent today

The good news is that the structure is already right. designer.py is split cleanly:

  • DesignerData (line 841) is a plain model. It holds the landmarks, the BT-only mode and offset, the unit, and it already has export_background_alog(filename) — a method that takes a path and writes a file, with no Qt in sight.
  • StandaloneDesignerWindow (line 1557) is the GUI, and it owns all the file I/O. save_draft_profile() and load_draft() open a QFileDialog as their first statement, so there is no way to call them with a path.

So the model is one method short of headless, and the blocker is that reading and writing drafts lives in the window instead of the data. Three small changes fix it:

  1. Move draft I/O into DesignerData — save_draft(path) and load_draft(path) as plain methods. The window keeps the file dialogs and calls them with whatever the user picked. No behaviour change for a human; a complete change for everything else.
  2. Add an entry point — python -m artisanlib.designer --landmarks … --out x.alog, or the same thing as an MCP tool. Once step 1 exists this is thin.
  3. Make the model validate. Port the script's refusals into DesignerData: reject a curve whose RoR rises through the roast, warn past ~12 °F/min, warn above the ~331 °F auto-heat cutoff, and refuse a curve that ends at DROP instead of tailing past it. Every one of these is a mistake that has actually been made on this machine.

Step 3 is the one that matters most, and it is worth stating why: validation in the model protects both paths at once. A rule that lives in the script protects only curves the script made. The same rule in DesignerData protects the script, the GUI, the CLI and any future MCP tool — because they would all go through it.

What this actually buys

Not "Claude can click the designer". The useful version is that designing a roast becomes a thing that can be reasoned about and checked rather than drawn:

  • Revise from evidence instead of memory. background-nudge-as-data proposes recording how far the plan was wrong, in seconds. That number is only useful if something can take a curve, apply the correction and write it back — which is exactly the headless path above.
  • Curves get checked before they reach heat. Today a designed curve is only tested by roasting it.
  • The machine facts stop living in a command file. They are currently prose in ~/.claude/commands/roast-design.md, true only for as long as someone reads it.

The thing to fix first is not code

make_roast_curve.py is the only tool that has ever produced a working curve for this roaster, and it sits in ~/Documents/Claude/Projects/roasting/ — outside git, unversioned, unbacked-up beyond Drive sync. Everything hard-won about this machine is in that file and in a markdown command beside it.

Move it into this repository before any of the work above. It is a copy and a commit, and until it is done the roast-design capability is one deleted folder away from gone. See the decision.

What was verified, and what was not

  • Verified Aug 6, 2026: that save_draft_profile/load_draft open a QFileDialog as their first statement (designer.py:2134, :2247); that export_background_alog(filename) is a method on DesignerData (:1001, class at :841) and takes a path; that the factory defaults are now medians of 46 recorded roasts; and that make_roast_curve.py is 205 lines with a parametric RoR model and its own input validation.
  • Not verified: that a headless DesignerData actually produces a loadable .alog without a Qt application existing. export_background_alog looks Qt-free, but the module imports Qt at the top, so constructing the class may still need a QApplication. Test this before promising the CLI — it decides whether step 2 is thin or awkward.
  • Not verified: whether the two tools currently disagree about the same roast. Nobody has generated one curve both ways and diffed them. That is a half-hour job and it would either confirm the drift or retire this concern.
  • Assumed: that the landmark model and the parametric model should converge rather than one replacing the other. They answer different questions — "hit these points" versus "decline this smoothly" — and the /roast-design command is emphatic that resampled curves are unreadable against a live roast. Converging the validation is clearly right; converging the models is not obviously right and is not proposed here.
