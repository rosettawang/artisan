An MCP server inside Artisan, and the four things being outside it costs

A working MCP bridge already exists outside Artisan and was verified against the real roaster on Aug 6, 2026. This spec is not "build an MCP" — it is "move it inside, and delete the parts that exist only to work around being outside."

Most of this already exists

Before specifying anything: ~/Documents/artisan-mcp is built, tested (102 passing checks across three suites) and has been driven against this roaster. It relays Artisan's Kaleido traffic over a WebSocket shim, injects guarded actuator commands, and exposes eleven MCP tools. The Kaleido protocol codec, the safety interlocks, the arm/disarm model, the audit log and the simulator all work and are portable as-is.

So the question this spec answers is narrow: what does being a separate process actually cost, and is that worth a fork? Four things, in descending order of how much they hurt.

Cost of being outsideWhy it exists
1. It cannot see the roast, only the wire. The bridge sees {0,BT:…,ET:…} frames. It has no access to aw.qmc.timeindex (CHARGE / DRY END / FCs / FCe / DROP), the profile, the background curve, phases, or statistics. It can report a temperature; it cannot answer "how long since first crack" or "am I ahead of the background profile" — which is most of what roast judgement is.
2. It cannot mark events. It fakes them by setting the low 4 bits of sid on a relayed frame. Artisan ignores those unless the Kaleido event flags are enabled (off by default), and per kaleido-machine-adaptations this machine reports sid=0 permanently, so the flags are inert here regardless. Inside Artisan, markChargeSignal.emit(True) is one line and always works.
3. It requires reconfiguring a working setup. Artisan must be switched from Kaleido serial to Kaleido WiFi (Config ▸ Device ▸ Networks) pointing at 127.0.0.1:8765, and the daemon must own /dev/cu.usbserial-0001. Only one process can hold a serial port, so every start/stop is a two-process handoff. Inside Artisan there is no handoff and no reconfiguration.
4. It reimplements code Artisan already has. artisan_mcp/protocol.py is a second implementation of the framing in artisanlib/kaleido.py. It was written by reading that file, and it will drift from it. Inside Artisan, aw.kaleido.send_msg() and send_request() already exist and are the only implementation.

Cost 1 is the one that justifies the fork. The others are annoyances; that one is a capability ceiling.

The transport is forced, and it is not stdio

Every MCP example is stdio. Artisan cannot use stdio — it is a GUI application that owns its own stdin/stdout, and there is no parent process launching it as a subprocess. The server must listen on a socket and Claude must connect by URL.

Verified Aug 6, 2026 against mcp==2.0.0: MCPServer exposes run_streamable_http_async, run_sse_async and streamable_http_app. Streamable-HTTP is the recommendation (see decision); SSE is the deprecated transport and a fork would carry it indefinitely.

There is already a precedent in-tree for this exact shape. artisanlib/weblcds.py runs an aiohttp server on a background thread with its own asyncio loop (WebView, _loop / _thread / _runner), started and stopped from the GUI. Copy that lifecycle rather than inventing one — same threading model, same shutdown discipline, same failure surface.

The one rule that will otherwise crash the app

Every mutation crosses into the GUI thread by Qt signal. No exceptions. The MCP server runs on a background thread; touching a widget, the matplotlib canvas, or qmc state directly from there is a use-after-free waiting for a busy roast. Artisan already defines the signals this needs — markChargeSignal, markDRYSignal, markFCsSignal, markFCeSignal, markDropSignal, markCoolSignal (see comm.py around the Kaleido_BTET handler, which emits exactly these from the sampling thread for the same reason).

Reads of plain Python attributes (aw.qmc.timex, aw.qmc.mode) are tolerable without a signal; anything that draws, records or actuates is not. When in doubt, emit.

What ports unchanged from the external bridge

  • safety.py — Limits, Guard, arm/disarm with expiry, the airflow interlock, the heater step cap, the BT/ET ceilings, the audit log. Move verbatim; it has the most test coverage and none of it depends on being out-of-process.
  • The tool surface and its docstrings — roast_status, roaster_probe, roast_arm, roast_disarm, set_heater, set_fan, set_drum, set_machine_pid, emergency_stop, mark_roast_event.
  • The INSTRUCTIONS block. It is the operating doctrine ("read status before and after every change", "a refusal is a correct answer").

What does not port: protocol.py (superseded by aw.kaleido), bridge.py's WebSocket relay (no longer a relay), roaster.py's SerialLink (Artisan owns the port), and daemon.py's Unix socket (no second process). The simulator is worth keeping in some form — see Phase D.

Dependencies: one line

Derived from src/requirements.txt on Aug 6, 2026 — re-run grep -nE '^(mcp|aiohttp|websockets|pyserial)' src/requirements.txt to confirm:

  • pyserial==3.5, websockets==17.0.1, aiohttp==3.14.3 — already dependencies.
  • mcp — the only addition. Requires-Python: >=3.10; Artisan's CI runs 3.14 (.github/workflows/mypy.yml), so it is compatible.

PyInstaller will need mcp reachable from src/artisan-mac.spec. Not verified: whether mcp's pydantic models need a hiddenimports entry. Find out by building, not by reasoning — pyinstaller artisan-mac.spec and launch the bundle.

Off by default, and bound to loopback

This server can command a burner. It must not be listening because Artisan happens to be open.

  • Default off. A toggle in Config (next to WebLCDs, which has the same character) turns it on for the session.
  • Bind 127.0.0.1 only, never 0.0.0.0. WebLCDs binds broadly on purpose — a phone on the same wifi is the point. This is the opposite: nothing outside the machine should reach it.
  • Arming still gates writes, exactly as in the external bridge. The listen toggle is not the arm.

Unbuilt roadmap

Ship each phase before starting the next. Delete this file when all are done.

A — Read-only server

src/artisanlib/mcp_server.py on the WebLCDs thread pattern, streamable-HTTP on loopback, Config toggle, one tool: roast_status. It reports what the external bridge could not — elapsed time, timeindex milestones with times, BT/ET/RoR from qmc, the machine actuators from aw.kaleido, and aw.qmc.mode as the authoritative unit. No writes at all in this phase. Proves the threading model against a real roast before anything can actuate.

B — Actuators, with the ported guard

Move safety.py in unchanged. Add set_heater / set_fan / set_drum / set_machine_pid / emergency_stop / roast_arm / roast_disarm, each writing through aw.kaleido.send_msg. The unit is now known for free from qmc.mode, so the fail-closed branch the external bridge needs (refusing heat when the unit is unknown) can be deleted rather than ported — but delete it knowingly, with a comment saying why it is safe here and was not there.

C — Roast events and the profile

The reason for the fork. mark_roast_event via the mark*Signal signals — real CHARGE and DROP, not sid bit-fiddling. Then read access to the background profile and phases so Claude can answer "am I ahead of the reference at this point in the roast", which is the actual question a roaster asks.

D — Simulator device, so none of this needs beans

Artisan already ships artisanlib/simulator.py. Wire the MCP tools to work against it so the whole surface can be exercised with no hardware and no fire risk — the role artisan_mcp/roaster.py's SimulatorLink plays today. Whether Artisan's simulator is rich enough to respond to heater changes is not verified; read it before assuming.

What is verified and what is not

  • Verified Aug 6, 2026: the protocol framing, the safety interlocks, the relay, and event injection — all under test in ~/Documents/artisan-mcp/tests/. The real machine answers PI and RD A0 over the real serial port through this code.
  • Never done, by anyone, ever: a write to this roaster from any of this code. No HP, FC, RC or TS command has been sent to the physical machine. Every actuator claim in this spec and in the bridge is inference from artisanlib/kaleido.py, not observation.
  • Not verified: that Artisan tolerates a second writer on aw.kaleido while its own sampling loop is polling. The external bridge serialises with a lock it owns; in-app, the write queue is aw.kaleido's. Read send_msg's queue discipline before Phase B.
  • Not verified: PyInstaller packaging of mcp.

Keeping the fork rebaseable

This is a fork of an active upstream (433 commits arrived between Nov 2025 and Aug 2026). Every file touched is a future merge conflict, so: put everything possible in one new file (mcp_server.py), and keep the main.py delta to a menu action plus start/stop calls. Do not refactor upstream code to make the MCP prettier. An upstream PR is unlikely to be accepted — an LLM control surface on a burner is not a general-audience feature — so assume this lives downstream forever and optimise for cheap rebases.
