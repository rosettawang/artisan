Loading a plan is not consenting to be driven by it

The burner handover is not a bug — it is three separately reasonable settings composing into an automatic one. Each was designed on its own; nothing in the UI shows they add up. This is the design principle that fixes it, the one-flag version of the fix, and the built-in answer to simplifying the UI.

Decided by the owner, Aug 6, 2026 — APPLIED by default. This spec recommended the opposite.

Owner: "I say On background load should be APPLIED by default. I am not usually running unguided roasts."

The recommendation above is superseded, and the reasoning behind it was incomplete. It argued that "a file should not silently rewrite the controller's tuning" — reasonable in the abstract, and wrong for this roastery. A background here is not a reference sketch; it is the plan the roast is actually driven from, with the PID following it (svMode = 2). Making its settings opt-in would mean pressing an extra button before every normal roast, which is the wrong default for someone whose normal case is a guided roast.

Precise scope of the reversal. What is withdrawn is "replace the four always-on flags with an explicit action". What survives — and what the finding was really about — is that the applying is invisible: loadpidfrombackground, loadRampSoakFromBackground, loadalarmsfrombackground and phasesfromBackgroundflag are on, hidden, and rewrite the controller with no statement that they did. Applying is correct here. Applying in silence is not.

So the code work becomes:

  • Keep applying on load, by default. No change to what happens for a normal roast.
  • Say what was applied. When a background load changes PID tuning, ramp/soak, alarms or phases, name it on the message line. One line, after the fact, not a prompt.
  • Make it a visible setting that defaults to on, rather than four hidden flags — "by default" implies something that can be turned off, and the four flags already exist to be surfaced.

This does not reopen the CHARGE-handover decision. That one is about the burner starting to drive itself when a roast begins; this one is about a file configuring the controller. Both are instances of the same principle — a reference action must not quietly become a control action — but the owner's answer here narrows that principle rather than abandoning it: quietly is the problem, not applying.

Read as a sequence: load a background → its tuning silently replaces yours → the setpoint starts following its curve → and the moment you mark CHARGE, the controller takes the burner. Three of those four are not Artisan defaults; this install turned them on. Each is defensible alone. Together they mean the act of opening a file decides who drives the roast.

That is exactly the reported symptom — "auto burner when background is loaded … that accidentally switches control" — and it is worth being precise about the trigger: the handover happens at CHARGE, not at load. Loading the file arms it; charging the beans fires it. That gap is why it feels accidental. By the time control changes hands, the file was opened minutes ago and is no longer on your mind.

The principle

Loading a plan is a reference action. Engaging the controller is a control action. A reference action must never become a control action on its own.

Everything below follows from that one line. A background profile is a reference — the shape you are trying to hit. Wanting to see it is not the same as wanting a controller to chase it, and the UI currently offers no way to say one without eventually getting the other.

The elegant fix is one flag

It is tempting to redesign the whole PID dialog. It is not necessary. Of the four settings, exactly one converts a loaded plan into a moving burner: pidOnCHARGE.

  • With it off, everything else stays inert. The background loads, its tuning is there, the setpoint would follow it — and nothing acts until you press the control on. You keep the whole "follow the background" workflow and lose only the surprise.
  • With it on, no amount of UI polish removes the trap, because the trigger is a roast event rather than a user action.

This is a settings change, not code. It is instantly reversible. It restores Artisan's own default. Do this first, and evaluate whether anything else is still wanted afterwards — the remaining items may well stop mattering.

Then: four hidden flags become one visible action

The deeper design problem is that background loading has four independent always-on flags, none of which announce themselves at the moment they fire:

FlagSilently overwrites
loadpidfrombackgroundPID tuning
loadRampSoakFromBackgroundRamp/soak programme
loadalarmsfrombackgroundAlarms — and upstream's own comment warns this "would overload the one of the foreground profile"
phasesfromBackgroundflagPhase boundaries

Four checkboxes in three different dialogs, each meaning "when I open a file, let it change my machine's behaviour". Nobody holds that model in their head while loading a profile.

Proposal: replace them with one explicit action. Loading a background always loads the curve. Applying its settings becomes a button — "Apply this background's settings" — that says what it will overwrite and does it once, when pressed. One action, visible, at the moment of intent, instead of four invisible ones firing at the moment of file-open.

This is strictly less code than it sounds: the four loadXFromProfile functions already exist and already do the work. The change is when they are called, not what they do.

Simplifying the UI: Artisan already did it

Artisan ships three UI modes (main.py:1353), and this install is on the busiest one:

ModeValueBehaviour
EXPERT1 — current settingEverything. Analyze menu, simulator, wheel editor, every LCD and slider entry.
DEFAULT2 — recommendedHides the expert-only tools; keeps the Tools menu, so the Designer stays reachable.
PRODUCTION3Hides the Tools menu entirely, plus buttons/sliders/PID-LCD entries unless already in use.

Do not jump to PRODUCTION. create_tools_menu is gated on ui_mode is not UI_MODE.PRODUCTION — the whole Tools menu disappears, and both Designers live in it. For a roastery that designs profiles, PRODUCTION removes the wrong things.

DEFAULT is one settings change, no code, instantly reversible, and it is the honest first move: find out how much of the clutter is Artisan being complex versus this install being set to EXPERT. Only design new UI for whatever still annoys after that.

If more is wanted after those three changes

Listed in order of value, none of them started:

  • One unambiguous "who is driving" indicator. Control state is currently spread across the CONTROL button, the PID LCDs, the slider positions and two dialogs. One persistent readout — burner: manual / burner: PID following background — would have made this whole class of confusion visible the first time it happened. This is the highest-value UI addition here, and the only one that would have prevented the original complaint.
  • Announce automatic transitions. If pidOnCHARGE is ever wanted again, it should say so in the message line when it fires. Silent handover is the actual defect; automatic handover is only a defect because it is silent.
  • Hide what this machine cannot do. This roaster reports no HS and no event flags (Findings 2 and 3), so any UI bound to them is dead weight on this install.
