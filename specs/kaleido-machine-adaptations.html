What this Kaleido actually reports, and the four places Artisan assumes otherwise

Four protocol facts, each measured against the real machine on Aug 6, 2026 — not read out of the driver. Three are harmless to Artisan and dangerous to anything outside it; one is a real usability bug worth fixing upstream.

The measurement

Taken with Artisan closed, holding /dev/cu.usbserial-0001 directly at 57600 baud. Re-derive with ~/Documents/artisan-mcp/doctor, or by hand:

{[PI]}       -> '{0}'
{[TU]}       -> '{0}'
{[SN]}       -> '{0}'
{[RD A0]}    -> '{0,BT:71.2,ET:72.1,AT:71.2,HP:0,FC:0,RC:0,AH:0,TS:32.0}'

Machine config, from ~/Library/Preferences/org.artisan-scope.Artisan.plist: device 138 (Kaleido BT/ET), kaleidoSerial = True, SerialPort.comport = /dev/cu.usbserial-0001, SerialPort.baudrate = 57600, Mode = 'F'. Adapter is a Silicon Labs CP210x (VID 0x10c4). Batch size shown in the UI: 100 g.

Finding 1 — the temperature unit is write-only

{[TU]} as a bare read returns a bare status frame. The machine accepts {[TU F]} as a set and never reports the unit back.

Artisan is unaffected, and this is worth stating clearly so nobody "fixes" it: Artisan sends TU from qmc.mode during ws_initialize / serial_initialize and never reads it. It already knows the answer; it is the one telling the machine.

The exposure is entirely outside Artisan. Any process reading this machine's frames without having sent TU itself sees 71.2 with no unit attached — and a Celsius safety ceiling checked against a Fahrenheit number is a live hazard: 480 °F reads as 480 "°C" (harmlessly conservative), but the reverse mapping is not. The external bridge now fails closed on this (refuses to add heat while the unit is unknown; reducing heat and emergency stop stay available). An in-app MCP does not need that branch at all — aw.qmc.mode is authoritative. See mcp-server Phase B.

No change to Artisan proposed. This finding exists to stop the fail-closed branch being ported in as cargo, and to stop anyone adding a TU read.

Finding 2 — sid is always 0, so the event flags are inert here

Artisan reads roast events out of the low 4 bits of sid (event_flag = _sid & 15 in comm.py's Kaleido_BTET): 1 CHARGE, 3 DRY END, 4 FCs, 5 FCe, 6 SCs, 7 SCe, 8 DROP. This machine has returned sid=0 on every frame observed, so _sid & 15 == 0 and no flag ever fires.

Consequence, both halves worth knowing:

  • Enabling the Kaleido event flags on this machine does nothing. All seven default to False (main.py:1822). Turning them on will not make CHARGE auto-mark, and time spent debugging that is wasted.
  • Equally, this machine cannot produce a false CHARGE. The upstream comment on that code says it plainly — "it remains unclear what those machines exactly report and when" — and a machine reporting a constant sid=1 would read as a permanent CHARGE. Ours reports 0. That risk does not apply here.

This was worth measuring precisely because the same trap bit the external bridge's simulator, which used sid=1 as its idle status and consequently announced a CHARGE on every poll.

Proposed change: a tooltip on the event-flag group in devices.py saying the flags depend on the machine reporting a non-zero low nibble, and that many do not. Cheap, honest, no state. See the decision against greying them out dynamically.

Finding 3 — no SN, no HS

{[SN]} returns a bare frame, and HS never appears in an RD A0 response. Both are declared in the State TypedDict, and get_state returns None for SN and -1 for HS when unset, so nothing crashes — the type assertions in getBTET / getSVAT / getDrumAH / getHeaterFan only cover BT ET TS AT RC AH HP FC, all of which this machine does report.

Two consequences:

  • kaleido.py:311 logs connected (None) at connect. Cosmetic, but it reads like a failure in a log you are scanning during a bad roast. Proposed: log connected (no serial number reported) when SN is absent.
  • There is no "is the burner actually firing" signal on this machine. HS is one of the two targets ({'CS','HS'} at main.py:9487) whose IO-command buttons update their state from the machine's response — on this roaster such a button would never light. Heater state must be inferred from HP > 0, which is a commanded value, not a confirmation. Anything that claims to verify the heater is off — including emergency_stop — is reporting an acknowledged command, not an observed state. Say so wherever it is surfaced.

Finding 4 — the CP210x wedge, and the only bug here worth upstreaming

Observed live on Aug 6, 2026. The adapter entered a state where the port opened and tcgetattr succeeded, but every tcsetattr failed with EINVAL (22) — including writing back byte-identical attributes.

What makes this diagnosable rather than mysterious is that it is not a Python or pyserial fault. The OS cannot configure the port either:

$ stty -f /dev/cu.usbserial-0001 57600
stty: tcsetattr: Invalid argument

Ruled out at the time: pyserial parameters (every combination including bare defaults failed), the /dev/tty. node, sandboxing, port ownership (nothing held it), USB enumeration (present, VID 0x10c4), and driver conflicts (IOSerialBSDClient bound normally, no third-party kexts). Unplugging and replugging the USB cable cleared it completely and the machine has been healthy since.

Proposed change, and the one with real user value: catch EINVAL specifically on serial open and surface "the USB adapter is not accepting configuration — unplug the cable, wait five seconds and plug it back in" instead of a generic serial failure. This is not Kaleido-specific: any Artisan user on a Silicon Labs adapter (Hottop, TC4, MODBUS serial) can hit it, and the generic message sends them to check baud rates, which is exactly wrong. Reference implementation and the full differential is in ~/Documents/artisan-mcp/artisan_mcp/doctor.py.

What is verified and what is not

  • Verified Aug 6, 2026, against this physical machine: all four {[…]} exchanges above, the stty failure and its resolution by replug, and that Artisan 4.2.0 connects and reads BT/ET over serial (observed 71.6 / 72.9 °F in the UI, 71.2 / 72.1 through the bridge minutes apart).
  • Read from source, not observed: every claim about what Artisan does with these values — the sid & 15 decode, the type assertions, the {'CS','HS'} button path, the event-flag defaults. Line numbers are against 784effc8.
  • Not verified — no write has ever been sent to this machine. Not HP, not FC, not RC, not TS. Whether it acknowledges a write with a single-var frame, how fast, and whether it tolerates a write between Artisan's polls are all unmeasured. The first write should be a fan or drum command on a cold empty machine, watched.
  • Unexplained: TS:32.0. 32 °F is 0 °C, which smells like an unset setpoint rather than a real target, but nothing confirms that. Do not build PID behaviour on an assumption about this value.
  • Unknown: the Kaleido model. The UI says 100 g; earlier in the same session it said 1 kg, so the batch size is a user field and not a machine identity. With no SN, the machine cannot be identified over the wire at all.
