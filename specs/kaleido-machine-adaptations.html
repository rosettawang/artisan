What this Kaleido actually reports, and where the fork drifted from it

Seven findings. Four are protocol facts measured against the real machine on Aug 6, 2026 rather than read out of the driver; three came from merging 433 upstream commits and finding that the fork had drifted — including a Kaleido RoR bug upstream fixed twice while this fork sat still.

Shipped Aug 6, 2026 — Findings 2, 3 and 4

The three items that needed neither the owner at the roaster nor a contended file are built. All in kaleido.py and devices.py; nothing here touches designer.py, main.py or pid_dialogs.py.

  • Finding 4 — the CP210x wedge. New diagnose_serial_error() in kaleido.py turns an opaque failure into a remediation line, and serial_connect logs it once per cause rather than on every retry of its forever-reconnect loop. EINVAL now says unplug the cable and explicitly says it is not a baud rate or port setting — which is where the generic message sent us for an hour. Also covers ENOENT (no such port), EBUSY (another process owns it) and EACCES.
  • Finding 3 — the connected (None) log. Both transports now log "no serial number reported" when the machine omits SN. The serial path did not log SN at all; it now matches the WebSocket path.
  • Finding 2 — the event flags. The checkbox tooltip in devices.py now says the flag only works if the machine reports events in the low 4 bits of its status word, and that many machines do not.

12 new unit tests (test_kaleido_diagnostics.py), 19 passing with the existing Kaleido suite. They pin the awkward part: termios.error carries (errno, msg) in args and has no .errno attribute, so both shapes must be recognised, as must a pyserial wrapper that only has the text.

Not verified: no wedged adapter was available to reproduce EINVAL through Artisan's own connect path — the classifier is unit-tested against constructed exceptions, not a live failure. The next real wedge is the test.

Incidental finding: pytest cannot even collect while an ArtisanViewer is running — importing artisanlib.main reaches sys.exit(0) at main.py:258 and pytest reports only "mainloop: caught unexpected SystemExit!". Close every Artisan instance before running the suite.

Answered by investigation, Aug 6, 2026 — the ET channel is format-filler here, and Finding 5 is fixed

The question was whether BT-only mode's generated ET is only there to satisfy the two-channel .alog format, or is read while roasting. Traced rather than guessed:

  • The PID does not read it. In Follow-background mode the setpoint comes from followCurveNr = self.pidSource (pid_control.py:1691), and for a non-TC4 device 1 means BT, 2 means ET (pid_control.py:1258). This install has pidSource unset, so the default 1 — BT — via backgroundSmoothedBTat. Follow mode is live: svMode = 2.
  • The only other functional reader is not enabled. Background ET feeds CM_ETBT, the Curve Match device (id 186, comm.py:574), which computes ET/BT deviation statistics. Configured extra devices are [141, 139, 140] — Kaleido Heater/Fan, SV/AT, Drum/AH. 186 is absent.
  • Everything else that touches temp1B is display — the background table in background.py and curve drawing in canvas.py.

So the -50 constant was never driving the roast, and the alarming version of this finding is retired. What was actually wrong was the labelling, and that is now fixed: the standalone designer reads Mode from Artisan's own settings and speaks that unit throughout — table headers, y-axis, the temperature-trigger placeholder, and the factory landmark defaults, which are written in Celsius and converted so they keep meaning the same roast (CHARGE 80 °C → 176 °F, DROP 210 °C → 410 °F). The offset converts as an interval: −50 °C → −90 °F, not −58.

Two things worth keeping in view:

  • This is configuration-dependent, not a property of Artisan. Set pidSource to 2 (ET) while Follow mode is on and the synthetic ET curve becomes the setpoint driving the burner. A comment at designer.py's et_offset says so.
  • Saved designer defaults carry no unit. load_defaults returns stored numbers as-is, so switching Artisan between C and F after clicking "Save as Default" will surface them unconverted. Not fixed — converting stored values on a guess would corrupt them. There are currently no saved defaults, so nothing is affected today.

Deliberately not changed: the default landmark values. Converting them is mechanical; replacing them with bay-nut numbers is a preference, and that decision belongs to designer-window. Note the converted defaults (DROP 410 °F) sit well above this roastery's actual practice — the roast log records 341–362 °F.

18 new unit tests (test_designer_units.py) pin the interval-vs-absolute distinction, since converting an offset with the absolute formula gives −58 and looks plausible.

The measurement

Taken with Artisan closed, holding /dev/cu.usbserial-0001 directly at 57600 baud. Re-derive with ~/Documents/artisan-mcp/doctor, or by hand:

{[PI]}       -> '{0}'
{[TU]}       -> '{0}'
{[SN]}       -> '{0}'
{[RD A0]}    -> '{0,BT:71.2,ET:72.1,AT:71.2,HP:0,FC:0,RC:0,AH:0,TS:32.0}'

Machine config, from ~/Library/Preferences/org.artisan-scope.Artisan.plist: device 138 (Kaleido BT/ET), kaleidoSerial = True, SerialPort.comport = /dev/cu.usbserial-0001, SerialPort.baudrate = 57600, Mode = 'F'. Adapter is a Silicon Labs CP210x (VID 0x10c4). Batch size shown in the UI: 100 g.

Finding 1 — the temperature unit is write-only

{[TU]} as a bare read returns a bare status frame. The machine accepts {[TU F]} as a set and never reports the unit back.

Artisan is unaffected, and this is worth stating clearly so nobody "fixes" it: Artisan sends TU from qmc.mode during ws_initialize / serial_initialize and never reads it. It already knows the answer; it is the one telling the machine.

The exposure is entirely outside Artisan. Any process reading this machine's frames without having sent TU itself sees 71.2 with no unit attached — and a Celsius safety ceiling checked against a Fahrenheit number is a live hazard: 480 °F reads as 480 "°C" (harmlessly conservative), but the reverse mapping is not. The external bridge now fails closed on this (refuses to add heat while the unit is unknown; reducing heat and emergency stop stay available). An in-app MCP does not need that branch at all — aw.qmc.mode is authoritative. See mcp-server Phase B.

No change to Artisan proposed. This finding exists to stop the fail-closed branch being ported in as cargo, and to stop anyone adding a TU read.

Finding 2 — sid is always 0, so the event flags are inert here

Artisan reads roast events out of the low 4 bits of sid (event_flag = _sid & 15 in comm.py's Kaleido_BTET): 1 CHARGE, 3 DRY END, 4 FCs, 5 FCe, 6 SCs, 7 SCe, 8 DROP. This machine has returned sid=0 on every frame observed, so _sid & 15 == 0 and no flag ever fires.

Consequence, both halves worth knowing:

  • Enabling the Kaleido event flags on this machine does nothing. All seven default to False (main.py:1822). Turning them on will not make CHARGE auto-mark, and time spent debugging that is wasted.
  • Equally, this machine cannot produce a false CHARGE. The upstream comment on that code says it plainly — "it remains unclear what those machines exactly report and when" — and a machine reporting a constant sid=1 would read as a permanent CHARGE. Ours reports 0. That risk does not apply here.

This was worth measuring precisely because the same trap bit the external bridge's simulator, which used sid=1 as its idle status and consequently announced a CHARGE on every poll.

Proposed change: a tooltip on the event-flag group in devices.py saying the flags depend on the machine reporting a non-zero low nibble, and that many do not. Cheap, honest, no state. See the decision against greying them out dynamically.

Finding 3 — no SN, no HS

{[SN]} returns a bare frame, and HS never appears in an RD A0 response. Both are declared in the State TypedDict, and get_state returns None for SN and -1 for HS when unset, so nothing crashes — the type assertions in getBTET / getSVAT / getDrumAH / getHeaterFan only cover BT ET TS AT RC AH HP FC, all of which this machine does report.

Two consequences:

  • kaleido.py:311 logs connected (None) at connect. Cosmetic, but it reads like a failure in a log you are scanning during a bad roast. Proposed: log connected (no serial number reported) when SN is absent.
  • There is no "is the burner actually firing" signal on this machine. HS is one of the two targets ({'CS','HS'} at main.py:9487) whose IO-command buttons update their state from the machine's response — on this roaster such a button would never light. Heater state must be inferred from HP > 0, which is a commanded value, not a confirmation. Anything that claims to verify the heater is off — including emergency_stop — is reporting an acknowledged command, not an observed state. Say so wherever it is surfaced.

Finding 4 — the CP210x wedge, and the only bug here worth upstreaming

Observed live on Aug 6, 2026. The adapter entered a state where the port opened and tcgetattr succeeded, but every tcsetattr failed with EINVAL (22) — including writing back byte-identical attributes.

What makes this diagnosable rather than mysterious is that it is not a Python or pyserial fault. The OS cannot configure the port either:

$ stty -f /dev/cu.usbserial-0001 57600
stty: tcsetattr: Invalid argument

Ruled out at the time: pyserial parameters (every combination including bare defaults failed), the /dev/tty. node, sandboxing, port ownership (nothing held it), USB enumeration (present, VID 0x10c4), and driver conflicts (IOSerialBSDClient bound normally, no third-party kexts). Unplugging and replugging the USB cable cleared it completely and the machine has been healthy since.

Proposed change, and the one with real user value: catch EINVAL specifically on serial open and surface "the USB adapter is not accepting configuration — unplug the cable, wait five seconds and plug it back in" instead of a generic serial failure. This is not Kaleido-specific: any Artisan user on a Silicon Labs adapter (Hottop, TC4, MODBUS serial) can hit it, and the generic message sends them to check baud rates, which is exactly wrong. Reference implementation and the full differential is in ~/Documents/artisan-mcp/artisan_mcp/doctor.py.

Finding 5 — an adaptation already exists, and it assumes Celsius

Written after the first four. This spec originally described a clean slate; it was wrong.

origin/main carried 11 commits of 2025 fork work that this branch merged forward on Aug 6, 2026 — including "Add Bean Temperature Only mode for Kaleido roasters" (602fcdb2c). That mode already exists in src/artisanlib/designer.py: it hides the ET controls and auto-generates the ET curve from BT, on the reasoning that Kaleido PID is BT-based.

The generation is one line — landmarks[name]['ET'] = data['BT'] + self.et_offset, with self.et_offset = -50.0 at designer.py:815. That constant carries no unit. The surrounding code assumes Celsius (the y-axis locator at designer.py:1349 is commented "Every 50°C"), but this Artisan runs Mode = 'F' and the owner's roast log records end temperatures in Fahrenheit (341–362 °F across 31 roasts).

So a profile designed in Fahrenheit with BT-only mode on gets an ET curve 50 °F below BT, where the design intent reads as 50 °C below BT — about half the gap, and the generated channel is written into the exported .alog.

Confirmed visually Aug 6, 2026, by launching the designer from source on Python 3.13 (python launch_profile_designer.py). It is not only the constant — the entire designer is hardcoded to Celsius and ignores qmc.mode: the landmark table headers read BT (°C) and ET (°C) (designer.py:1560, :1562), and the chart's y-axis is labelled Temperature (°C) (designer.py:1227). The default landmarks it opens with are Celsius values too — CHARGE 80, DRY_END 150, FC_START 190, DROP 210 — which are sane in °C and meaningless in °F. Meanwhile Mode = 'F' in the owner's settings and every roast in the log is in Fahrenheit.

So the mismatch is wider than et_offset: a Fahrenheit roaster typing Fahrenheit numbers into fields labelled °C gets a curve that is internally consistent and mislabelled, and an exported .alog whose unit is whatever the importer assumes. The -50 offset is one symptom of a designer that was written in Celsius and never taught about the app's mode.

Proposed change: make the offset unit-aware — either scale it by the active mode, or label the input field with the unit and store what the user typed. Not yet established which is right, because it is not established what the ET channel is for here: if it exists only to satisfy the two-channel .alog format, the offset barely matters and a label is enough; if it is used as a reference curve while roasting, it matters a lot. Answer that before changing the number.

Finding 7 — the cap-burner flag duplicates a control upstream already had ✅ Removed Aug 6, 2026

Decided and done — owner answered "delete the cap burner checkbox", Aug 6, 2026

capBurnerOutputFlag, both copies of capBurnerOutputSlot and their orphaned @pyqtSlot decorators are gone. Use upstream's Max spin box in the duty-clamp group (Config ▸ PID ▸ Duty, pid_dialogs.py:554) — it does the same job at any value, not only 80%.

Removing it turned up collateral damage. The 2025 fork's diff to pid_dialogs.py was not only the checkbox — it also silently carried three unrelated changes, none of them a feature:

  • deleted setFocusPolicy(Qt.FocusPolicy.NoFocus) from both Ramp/Soak "Load from profile" and "Load from background" checkboxes
  • deleted a commented-out slider line in PXG4pidDlgControl
  • changed C2Widget.setLayout(svlayout) to tab2Layout in PXRpidDlgControl — the wrong layout on the SV tab, which is a real bug rather than a cosmetic drift

All three are restored. src/artisanlib/pid_dialogs.py is now byte-identical to upstream/master, which is the strongest possible statement that nothing of the fork's remains in it. Verify with git diff --quiet upstream/master -- src/artisanlib/pid_dialogs.py.

The general lesson, worth carrying into the MCP work: this fork's diffs contain edits nobody intended. When a fork feature is removed, diff the whole file against upstream rather than just deleting the feature's own lines.

The original finding, kept because the reasoning is what justified the removal:

The 2025 fork added capBurnerOutputFlag to pid_dialogs.py: a checkbox labelled "Cap Burner Output at 80%" whose slot sets pidcontrol.dutyMax = 80.

Upstream already ships that control. pid_dialogs.py:554 defines a dutyMax spin box with range −100…100 and step 10, in a Max/Min duty-clamp group next to dutyMin. The fork's checkbox is a hardcoded preset for one value of it.

It is also subtly wrong as written. Its checked state comes from self.aw.pidcontrol.dutyMax == 80, evaluated once at dialog construction — so setting the spin box to 75 leaves the checkbox unchecked while the burner is still capped, and two controls disagree about the same underlying value. Two widgets writing one setting, one of them with a hardcoded constant, is a bug waiting for the day the cap is wanted at 70.

It survived the merge unchanged because deleting a fork feature is the owner's call, not a merge conflict resolution. See the decision.

Worth knowing while deciding: the PID subsystem around it is not the one that was forked — 24 commits hit pid_dialogs.py, adding 2DOF PID (beta/gamma), gain scheduling, a derivative filter and limit, an output filter, bump-less MANUAL↔AUTO transfer and SV FIR filtering. Any remembered PID behaviour from 2025 should be re-checked rather than trusted.

What is verified and what is not

  • Verified Aug 6, 2026, against this physical machine: all four {[…]} exchanges above, the stty failure and its resolution by replug, and that Artisan 4.2.0 connects and reads BT/ET over serial (observed 71.6 / 72.9 °F in the UI, 71.2 / 72.1 through the bridge minutes apart).
  • Read from source, not observed: every claim about what Artisan does with these values — the sid & 15 decode, the type assertions, the {'CS','HS'} button path, the event-flag defaults. Line numbers are against 784effc8.
  • Not verified — no write has ever been sent to this machine. Not HP, not FC, not RC, not TS. Whether it acknowledges a write with a single-var frame, how fast, and whether it tolerates a write between Artisan's polls are all unmeasured. The first write should be a fan or drum command on a cold empty machine, watched.
  • Unexplained: TS:32.0. 32 °F is 0 °C, which smells like an unset setpoint rather than a real target, but nothing confirms that. Do not build PID behaviour on an assumption about this value.
  • Unknown: the Kaleido model. The UI says 100 g; earlier in the same session it said 1 kg, so the batch size is a user field and not a machine identity. With no SN, the machine cannot be identified over the wire at all.
