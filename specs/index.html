  • A roasting UI with only the buttons this roast needs open

    Asked for as "a simplified UI more tailored to just the buttons I need, that can be dropped". Almost all of the machinery already exists and is already configured on this install — there are ten switchable button palettes, eight of them empty.     A working MCP bridge already exists outside Artisan and was verified against the real roaster on Aug 6, 2026. This spec is not "build an MCP" — it is "move it inside, and delete the parts that exist only to work around being outside."

  • Listening for cracks, and using the machine's own state to know what to ignore open

    Record the roast, separate crack transients from drum and fan noise, and turn crack density into a number that can inform the drying phase. Artisan has no audio input of any kind today, so all of this is new. Low priority — filed to be ready, not to be built next.

  • Loading a plan is not consenting to be driven by it open

    The burner handover is not a bug — it is three separately reasonable settings composing into an automatic one. Each was designed on its own; nothing in the UI shows they add up. This is the design principle that fixes it, the one-flag version of the fix, and the built-in answer to simplifying the UI.

  • Nudging the background is a measurement, and Artisan throws it away open

    You move the background left or right when the roast stops matching the plan. That act is the most honest measurement in the whole session — it is the roaster saying, in seconds, exactly how wrong the plan was. Artisan tracks the number in memory, resets it to zero in five different places, and never writes it to disk.

    Remaining: Steps 1 and 2 shipped Aug 6, 2026 (offset persisted, per-nudge history recorded, PID-follow warning). Steps 3 and 4 are PARKED, not blocked by a person: they analyse nudge history across roasts, and no saved profile contains any yet — the field was only added today. They become buildable once a few roasts have been recorded with it. Nothing to decide; it needs elapsed time.

    Twelve Designer complaints, a PID request and a hardware question, written against a 2025 Artisan and handed over on Aug 6, 2026. Checked one by one against the merged 4.2.1 tree: four are already shipped, one was built and deleted the same day, two have a single shared root cause, and one cannot be specified because its screenshots are missing.

  • Two roast designers, and only one of them Claude can use open

    Asked directly: am I using the roast designer tool? No — and neither does the established workflow. Curves for this machine are generated by a 205-line script that lives outside this repository, while the designer in the fork has never produced one. Two tools now make background profiles, they know different things, and neither knows what the other knows.

  • What this Kaleido actually reports, and where the fork drifted from it open

    Seven findings. Four are protocol facts measured against the real machine on Aug 6, 2026 rather than read out of the driver; three came from merging 433 upstream commits and finding that the fork had drifted — including a Kaleido RoR bug upstream fixed twice while this fork sat still.

  • Who cuts the heat at 165 °C, and can software override it open

    Every roast on this machine dies in a 14 °F band. Artisan's four automatic DROP paths are ruled out by measurement, and one roast proves the machine cuts its own heat unprompted — but nobody has yet watched the wire at the moment it happens, and that single recording decides whether this is fixable in software or is a machine limit to design around.

Bottlenecks

Hand-maintained. What is worth doing first, as opposed to what the dependency graph permits.

  • The write path is the whole risk, and it is still untouched. Reads are free and reversible; a burner command is neither. Hardware-pass row 3 gates more than it looks like it does — no write of any kind has ever reached this roaster, so every actuator behaviour in both specs is inference from artisanlib/kaleido.py. This is the single largest gap between what this repo claims and what has been observed.
  • Nothing is proven against a moving roast. Updated Aug 6, 2026: the merge itself is now proven — 2359 tests pass with zero regressions, the app and the standalone designer both run from source. What remains unproven is behaviour under heat. Every temperature claim was measured on a machine at room temperature, and the interlocks have never refused a real command during a real roast. Prefer the phases that reach a watched, beanless heated run over the phases that add tools.
  • The fork's diffs contain edits nobody intended. designer.py and main.py have not been audited the same way. ✓ Audited Aug 6, 2026 — clean. designer.py is a strict superset of upstream's (zero upstream lines lost, verified by git diff upstream/master -- src/artisanlib/designer.py | grep "^-" returning nothing). main.py's fork delta is coherent, and the merge restored designerAction to __slots__ alongside the fork's two additions, with all 3 setEnabled call sites matching upstream. canvas.py and pid_dialogs.py are byte-identical to upstream. The collateral damage was confined to pid_dialogs.py and is fixed.
  • A running bridge owns the roaster. Learned the hard way (hardware-pass row 2): one process holds the serial port, and if it is not Artisan then Artisan is blind. Never leave the bridge running across a change of topic, and never while anyone might roast.
  • Lowest priority, by the owner's own call: crack-listener. Filed to be ready, not to be built next. It also has the cheapest kill test in the whole folder — record one roast on a phone near the drum and listen back. If a human cannot hear cracks over the fan, close the spec. Do that before it is ever scheduled.
  • Rebase cost compounds. The longer this fork sits behind upstream, the more each spec's spec-touches hurts — and the 433-commit gap meant roasting on a knowingly-broken Kaleido RoR for months. Pull upstream before starting a phase, not after.

How specs get worked

Spec pass — how specs get worked, by default. No further prompting should be needed: the session runs the whole thing without asking what to do next.

  1. Reassess the spec first. A spec is a starting point, not a contract. Check its claims against the current code and the machine before building — specs here go stale, and this one's neighbours went stale inside a single session. Where reality has moved, correct the spec and say what changed.
  2. Sequence it, then work the sequence end to end. Don't stop after one item to report progress, and don't ask which item to do next.
  3. Use discretion to build it out. Fill gaps the spec left, fix what it got wrong, improve on it where the better design is clear. Note the deviations.
  4. Stop only at a blocker or a decision — a step needing the owner at the roaster, anything that puts heat into a drum, or a choice that is structural and hard to reverse. Not on mere uncertainty: if a call is cheap and reversible, make it, note it, keep going. "Stop" means stop that spec, never the session.
  5. Log the stop in that spec's spec-blocker meta, then run ./specs.sh prune so the index reflects it.
  6. Declare each decision separately, one spec-decision meta per choice, stating the recommended answer and whether it blocks. Burying a decision in blocker prose leaves it unfindable.

Verify as you go rather than at the end — but be honest about what verification is available here. The suite needs Python 3.12+, and no test in this repo can tell you whether a burner command did what you expected. That answer only comes from standing at the machine.

Conventions — the metadata a spec declares
MetaMeaning
spec-statusopen | blocked | done | canonical. Required. prune deletes the done ones and logs a dated completion note.
spec-touchesSpace- or comma-separated paths the spec edits. Drives conflict detection and ordering. In this fork it doubles as the rebase-cost estimate.
spec-needsSlugs that must land first.
spec-blockerOne dated line of what remains. If nobody can unblock it, it is parked — say so.
spec-decisionOne per owner choice, with the recommended answer and whether it blocks. Never bury a choice in blocker prose.
spec-verifyA shell command that exits 0 when the spec is genuinely done.
