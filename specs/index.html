Bottlenecks

Hand-maintained. What is worth doing first, as opposed to what the dependency graph permits.

  • The write path is the whole risk, and it is still untouched. Reads are free and reversible; a burner command is neither. Hardware-pass row 3 gates more than it looks like it does — no write of any kind has ever reached this roaster, so every actuator behaviour in both specs is inference from artisanlib/kaleido.py. This is the single largest gap between what this repo claims and what has been observed.
  • Nothing is proven against a moving roast. Updated Aug 6, 2026: the merge itself is now proven — 2359 tests pass with zero regressions, the app and the standalone designer both run from source. What remains unproven is behaviour under heat. Every temperature claim was measured on a machine at room temperature, and the interlocks have never refused a real command during a real roast. Prefer the phases that reach a watched, beanless heated run over the phases that add tools.
  • The fork's diffs contain edits nobody intended. Removing one feature from pid_dialogs.py turned up three unrelated changes, one a real bug. designer.py (1418 added lines) and main.py have not been audited the same way. Do that before building on either — it is cheap now and expensive after new code sits on top.
  • A running bridge owns the roaster. Learned the hard way (hardware-pass row 2): one process holds the serial port, and if it is not Artisan then Artisan is blind. Never leave the bridge running across a change of topic, and never while anyone might roast.
  • Rebase cost compounds. The longer this fork sits behind upstream, the more each spec's spec-touches hurts — and the 433-commit gap meant roasting on a knowingly-broken Kaleido RoR for months. Pull upstream before starting a phase, not after.

How specs get worked

Spec pass — how specs get worked, by default. No further prompting should be needed: the session runs the whole thing without asking what to do next.

  1. Reassess the spec first. A spec is a starting point, not a contract. Check its claims against the current code and the machine before building — specs here go stale, and this one's neighbours went stale inside a single session. Where reality has moved, correct the spec and say what changed.
  2. Sequence it, then work the sequence end to end. Don't stop after one item to report progress, and don't ask which item to do next.
  3. Use discretion to build it out. Fill gaps the spec left, fix what it got wrong, improve on it where the better design is clear. Note the deviations.
  4. Stop only at a blocker or a decision — a step needing the owner at the roaster, anything that puts heat into a drum, or a choice that is structural and hard to reverse. Not on mere uncertainty: if a call is cheap and reversible, make it, note it, keep going. "Stop" means stop that spec, never the session.
  5. Log the stop in that spec's spec-blocker meta, then run ./specs.sh prune so the index reflects it.
  6. Declare each decision separately, one spec-decision meta per choice, stating the recommended answer and whether it blocks. Burying a decision in blocker prose leaves it unfindable.

Verify as you go rather than at the end — but be honest about what verification is available here. The suite needs Python 3.12+, and no test in this repo can tell you whether a burner command did what you expected. That answer only comes from standing at the machine.
