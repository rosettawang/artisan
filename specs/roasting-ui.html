Governing principle, set by the owner Aug 6, 2026

"You're supposed to build [the interface] off of what buttons I click."

So this spec is not "pick a sensible subset of Artisan's controls". It is: instrument which controls are actually pressed during real roasts, and derive the interface from that record. A button palette chosen by reasoning about what a roaster probably needs is a guess; a palette chosen from a month of logged presses is a measurement.

Two consequences worth stating before any layout is drawn:

  • Instrumentation comes before design. Log every event-button and slider action with its roast time. Artisan already records event actions into the profile, so much of this may be recoverable from the 46 existing .alog files without writing anything — check that before building a logger.
  • The evidence outranks the recommendation. If the log says a control this spec calls essential is never touched, the log wins.

This also settles why the UI_mode question was withdrawn: choosing among Artisan's three built-in menu presets is configuring someone else's design. Building from click evidence is the point of the fork.

A roasting UI with only the buttons this roast needs

The governing principle says derive the interface from what is actually pressed, and check the existing profiles before building a logger. Checked: no logger is needed. What this does to the palette already built

Mostly vindicated, one real gap. Burner and air ++/-- are the right primitives — fine adjustment is 57.9% of all burner activity. Giving drum a slider and no buttons matches 0.7% usage at essentially one value. And Damper should be removed from the event types entirely: it occupies a channel and has never been touched in 69 roasts.

The gap is the other 42%: jumps larger than 10% are frequent, and the minimal palette has no way to make one except dragging the slider. The earlier claim that "the sliders make the grid redundant" is half right — right for fine work, wrong for jumps. Before adding jump buttons, note the destination values are near-uniform across 0–80% with no favourites (45%×1205, 60%×1184, 35%×1126, 80%×1111 …), so there is no small set of presets to add. That is an argument for the slider, not for eight more buttons — but it should be settled by trying palette 3 for one roast and seeing whether reaching for the slider feels worse than the grid did.

Re-derive with: parse specialeventstype/specialeventsvalue from the profiles, decoding each value as (v−1)×10 percent.

Verified through Artisan's own parser, Aug 6, 2026. The file was pushed through aw.loadPalettes() headlessly — the real code path an import takes, minus the file dialog. It returns the maxlen list, palette 3 comes back with 8 buttons and 6 visible, palettes 1 and 2 come back at 42 and 16, the sliders arrive as ['kaleido(FC,{})', 'kaleido(RC,{})', '', 'kaleido(HP,{})'] with visibility [1,1,0,1], and the other seven slots stay empty.

That run caught a defect the structural checks missed. The nudge buttons were labelled ◀ and ▶, and they came back through decodeTreeStrings as â\x97\x80 bg — UTF-8 bytes read as Latin-1. The labels would have rendered as garbage on the button faces. Relabelled << bg / bg >> and re-verified. Keep palette labels ASCII.

The one thing that is actually missing — it was not missing

Withdrawn Aug 6, 2026. This section was wrong.

It claimed palette switching "is buried" and proposed a selector on the main window — the only code in this spec. Artisan already has the switch, and it is better than the one proposed: buttonpalette_shortcuts defaults to True and ⌘+number switches palettes directly (main.py:12411). It is not saved in this install's settings, which means it is on at its default.

It is also smarter than a combo box: the call is setbuttonsfrom(n, only_non_empty=True), so ⌘4–⌘9 do nothing rather than blanking the button area on an empty slot.

So ⌘3 loads the minimal set and ⌘1 puts the full grid back. That is exactly the "can be dropped" the request asked for, and it needs no code at all. Step 3 below is cancelled; this spec is now pure configuration.

The lesson is the one this repo keeps relearning: the claim was written from reading the settings and the palette structures, not from searching for a shortcut. Grep for the feature before specifying it.

What the minimal set should contain

Derived from what this session actually watched being used and from the 46 recorded roasts, rather than from a survey:

┌────────────────────────────────────────────────────────┐
│  OFF      START            CHARGE      DROP            │   ← run the roast
├────────────────────────────────────────────────────────┤
│  Burner  ▁▂▃▄▅▆▇   Air  ▁▂▃▄▅▆▇   Drum  ▁▂▃▄▅▆▇        │   ← the three sliders
├────────────────────────────────────────────────────────┤
│  ◀ background          offset −40s          background ▶│   ← the nudge, with its number
└────────────────────────────────────────────────────────┘

Three notes on that sketch, each with a reason:

  • Sliders, not the 42-button grid. Palette 1 spends 42 buttons on discrete percentages (100%, 90%, 80% …) for three actuators that already have continuous sliders on the left of the window. The grid is faster for a known value and worse for everything else; the sliders are already there and already work.
  • DRY END, FCs, FCe stay available but off the minimal set. They are marked in 14, 13 and 10 of 46 roasts — real but not every-roast. Hiding them is reversible per-button.
  • The background nudge earns its place, because this install nudges routinely — movespeed is set to 50 against a default of 30. Showing the accumulated offset next to the control is new, and is where the nudge stops being invisible.

The second one is the point of contact with control-handover-and-ui: a simplified UI must not simplify away the fact that something else is driving the burner. Fewer buttons is only an improvement if the state that matters stays visible. If the two specs disagree, that one wins — it is about heat and this one is about convenience.

Order, and what it depends on

  1. Build the palette in an empty slot (3–9). Pure configuration, zero code, instantly reversible — palette 1 is untouched and one switch away. Try it on one roast before anything else is built.
  2. Hide the default buttons that are not earning their space. Also configuration, per-button, reversible.
  3. Add the palette selector to the main window. Cancelled — ⌘+number already does it (see above).
  4. Show the background offset next to the nudge. Needs background-nudge-as-data, whose persistence and per-nudge record shipped Aug 6, 2026.

What was verified, and what was not

  • Verified Aug 6, 2026 against this install's settings: ten palette slots with 42 and 16 buttons in slots 1 and 2 and eight empty; all eight default buttons visible; the UI_MODE enum and its three values; movespeed = 50; and the landmark-marking frequencies (CHARGE and DROP in 46 of 46 roasts, DRY END 14, FCs 13, FCe 10, SCs 10, SCe 8).
  • Not verified: that switching palettes mid-roast is safe. It rebuilds the button area while a roast is recording, and nothing here has tested that. Check it on a beanless run before trusting it during a roast.
  • Not established: whether the 42-button grid is genuinely unused or used for speed in a way the sliders cannot match. This spec assumes the sliders suffice; that assumption is the owner's to overturn, and it is the substance of the open decision.
